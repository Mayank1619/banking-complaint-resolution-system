# Database Schema Workbook

## Objective
Create the core relational structure that supports complaint tracking, customer context, evidence, and operational reporting.

## Business problem
The bank needs a durable relational foundation that can store customers, accounts, complaints, and supporting evidence in a queryable format.

## Requirements gathered
- Define key entities, relationships, and constraints for the complaint domain.
- Model customer, account, complaint, and evidence tables with clear keys and status fields.
- Capture operational and reporting needs such as complaint categorisation and resolution status.
- Ensure the schema is ready for down-stream SQL and API integration.

## Key outputs to produce
- Stakeholder and scope overview
- Functional requirements and constraints
- Quality gates and edge cases
- Acceptance criteria tied to the sprint objective
- Clear handoff notes for downstream work

## Success metrics
- Complaint data is stored consistently and queryable.
- Relationships between customers, accounts, and complaints are clear.
- Reporting and analysis are grounded in a reliable schema.
- The data layer supports later AI and service workflows.

## Handoff
The relational schema becomes the trusted data foundation for analysis, interrogation, and application integration across the project.

## Completion status
Completed as the actual solution for this exercise in the banking complaint-resolution programme.
